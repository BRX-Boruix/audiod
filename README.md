# audiod

BORUIX 的**用户态音频混音守护进程**：把多路音频输入混音后送往输出设备。

[English](README.en.md)

## 它做什么

```
生产者(们) → stream/0..3 → audiod（混音） → dsp → 硬件驱动 → 硬件
```

多路输入各自写入一个音频流节点，本进程把它们**混音成一路**，写入输出设备，由硬件驱动读走。

当前能力：

| 能力 | 说明 |
| --- | --- |
| **多路混音** | 最多 4 路输入混合为一路输出 |
| **缺路容错** | 某路未连接不影响其余路——宁可少混几路，也不因一路缺失而整体失败 |
| **采样率转换** | 输入采样率与输出不一致时按比例转换 |
| **音量调节** | 带渐变，避免音量突变产生的爆音 |
| **欠载统计** | 记录各路的连接状态与数据供给不足的情况 |

## 为什么混音放在用户态

内核的音频节点是**哑管道**——对 PCM 内容零知识，只负责搬字节。混音是**策略而非机制**，放在用户态
才能在不改内核的前提下迭代算法。

代价是引入一个中间层。这个代价值得付：算法会反复调整，而内核应当保持稳定；把会变的东西放在会变
的地方。

## 独占输出的顺序约束

输出设备是**独占消费者**语义——必须先"附加"才能写入，且本进程一旦附加就**永不分离**（它是守护
进程）。

因此任何其他需要附加该设备的程序都**必须在本进程之前启动**。启动顺序已按此约定排列。

## 失败时的行为

| 情况 | 处理 |
| --- | --- |
| 输出设备已被别的消费者占用 | 如实报错并**退出** |
| 输入或输出节点打不开 | 如实报错并退出 |
| 输入暂时无数据 | **跳过本轮**，不是错误 |
| 输出缓冲已满 | 让出 CPU 后**重试同一段数据**，绝不丢弃 |
| 其他硬错误 | 如实报错并退出（不静默消失） |

所有失败路径都返回非零，启动它的流程能如实观察到"混音器挂了"。

## 构建

```bash
cargo build --release
```

由系统初始化进程在启动时拉起，之后常驻运行。

## 文件结构

```
audiod/
├── Cargo.toml    # 包定义
├── build.rs      # 注入链接脚本
├── linker.ld     # 用户态段布局
└── src/
    └── main.rs   # 混音循环与失败处理
```
